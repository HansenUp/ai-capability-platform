# ADR-0003 统一接入网关选 APISIX，自研插件承担节点路由与身份注入

- 状态：已采纳
- 日期：2026-10-16
- 关联需求：RT-20、CS-05、UC-02、TP-06
- 依据：实施计划 S10.4、S10.7；ADR-0011（执行者身份由平台签发，不接受客户端自称）

## 背景

集中式拓扑下存在多个 Runtime 节点组。同一个 Agent 需要按绑定关系与权重落到指定节点组，节点上下线、心跳超时需要及时反映到入口；同时下游服务必须拿到可信的调用者身份，而不是客户端自称的身份。

这三件事（身份验签与注入、路由、节点健康）都发生在入口，放在每个 Runtime 里各做一遍既重复又无法统一治理。Console API 已提供路由表（`GET /routing`），内容包括节点组到节点的分布、Agent 到节点组的绑定与权重、默认节点组以及生成时间，心跳超时的节点已被剔除。

## 决策

统一接入网关选用 Apache APISIX，并自研一个路由插件，职责限定为：

1. 路由：从 Console API 的 `/routing` 周期拉取路由表并缓存在网关本地；请求到达时按 Agent 的绑定与权重选择节点组，再在组内选择节点转发。无绑定的 Agent 使用路由表中的 `default_group`。
2. 身份注入：先按 JWKS 本地验签（`JWKS_URL` 指向 Keycloak realm 的证书端点），验签通过后从令牌解析主体、执行者（`act`）与租户，写入约定的身份头再转发。客户端自带的同名身份头一律先剥离再注入，不信任客户端自称。身份头的具体名称在 S10.4 实现时与 `services/runtime/src/runtime/api/auth.py` 对齐。
3. 降级：Console API 不可用时照常转发。具体规则：
   - 拉取失败时继续使用最后一次成功的缓存，过期不作废（失败时沿用旧表）；
   - 网关冷启动且尚无任何缓存时，退回插件配置中的静态默认节点组，不拒绝请求；
   - 缓存期间可能指向已下线节点，依靠上游主动与被动健康检查加重试排除，不依赖路由表实时性。
4. 拉取周期、缓存超过多久触发告警，作为插件配置项，初始拉取周期取 10 秒，随 S10.4 联调确定。
5. 插件不做授权判定、不做业务路由规则、不缓存业务数据。授权仍由策略服务与能力网关负责（ADR-0001、ADR-0009）。

## 备选方案

在 Runtime 前放自研反向代理：要自己实现健康检查、负载均衡、JWT 验签与热更新，属于已被成熟网关覆盖的能力，与 ADR-0007 冲突，不采纳。

Kong 或 Envoy 加外部授权：同样可行，但需要额外的外部服务才能完成"拉取路由表加权重选择"，APISIX 的自定义插件机制与动态上游更直接，保留为替换路径。

让 Console API 直接做请求代理：把管理面放到请求热路径上，Console 故障会拖垮业务请求，与"Console 不可用时照常转发"的目标矛盾，不采纳。

## 后果

- 新增部署对象 APISIX（以及其配置存储），插件代码放在 `deploy/apisix/plugins/`；路由表接口 `/routing` 成为网关与 Console 之间的契约，字段变更需走接口变更流程。
- 路由变更不是瞬时生效，生效延迟约等于拉取周期；对灰度节点组切换这类操作需把该延迟计入演练口径。
- Console 不可用期间新注册的节点和新增的绑定无法生效，属于可接受的降级，需要在 Console 可用性告警中覆盖。
- 本机开发不依赖 APISIX：本机直连 Runtime（:8080），APISIX 相关验证推迟到 S10。

## S10.4 本机实现细化（2026-10-18）

拉取接口使用独立 JWT 只读服务端点 `/internal/routing`，保留 `/routing` 给现有开发管理页面。缓存必须按租户和完整可信配置隔离，节点 ID 仅映射静态白名单；已有 Run 仅在明确共享状态池中路由，不重新套用 Agent 当前权重。具体身份、状态池及失败关闭边界见 `docs/decisions/2026-10-18-S10路由契约.md`。

真实 APISIX 3.11 验证确认 `upstream.set` 不自动初始化原生 checks；本机插件采用显式有界健康探测及被动失败记录，避免写了 checks 却没有实际隔离，也不使用全故障时回到坏节点的默认行为。读写均 retries=0，不自动重放副作用。活跃请求按周期触发异步刷新，空闲无轮询；缓存失败沿用、冷启动显式静态回退的决策不变。本机验证不等同生产部署、容量、TLS 或网络边界验收。
