# ADR-0009 授权多条件合取与范围审批

- 状态：已采纳
- 日期：2026-09-12
- 关联需求：CG-16、CG-17、SC-02
- 依据：外部设计评审第 03 条；代码核查确认为现存缺陷

## 背景

原策略中高风险写的放行条件仅为风险等级为高风险写且上下文标记已审批，没有约束租户、主体与数据范围。Cedar 多条 permit 取并集，任一条命中即放行，不会自动把多条许可的条件求交集。因此跨租户的高风险写只要带上已审批标记即可通过。Python 基线评估器存在同样问题。这是代码中的真实越权，而非文档层面的隐患。

另有两处语义问题。其一，审批凭据不绑定具体参数与资源，审批通过后参数被改动仍可执行。其二，Cedar 原生只返回允许与拒绝两种判定，需审批是平台授权服务合成的第三态，切换到真实引擎时若假设引擎会返回它将直接失效。

## 决策

执行条件改为多条件合取：基础权限成立、Agent 能力范围允许、数据范围允许、本次审批有效，四者同时满足才放行。跨租户调用由独立的 forbid 规则兜底，优先于所有 permit，确保后续新增 permit 也无法绕过租户边界。审批不能替代基础权限。

审批改为范围授权。审批凭据绑定调用标识、参数哈希、目标资源、预演结果、审批人与有效期。正式执行前重新校验参数哈希与有效期，参数变化或超时后必须重新审批。业务侧工具应提供批量接口，使一次审批覆盖一批操作，避免逐条审批导致不可用。

需审批状态明确记为平台授权服务的合成态。迁移到真实 Cedar 引擎时用两次查询或独立策略集表达，不得假设引擎直接返回。

## 备选方案

在每条 permit 上分别追加租户条件而不加 forbid。可修复当前问题，但无法约束将来新增的 permit，不采纳。

会话级预授权，即本次 Run 内同类操作一律放行。可用性好但风险过高，不采纳。

## 后果

策略文件、基线评估器与共享用例集同步修改，新增跨租户与审批相关的否定用例。审批接口增加参数哈希与有效期字段，闸口的已批准集合从标识集合改为带参数哈希与过期时间的映射。前端审批卡片需携带参数哈希。业务系统需提供批量接口，该要求进入 MCP 工具上架规范。
