# S14.1 候选 A 权威／见证隔离状态机契约（本机模型）

用户已同意候选 A 的方向并授权本机验证。以下选择仅固定测试状态机，不确定正式产品、见证服务、密钥托管或运维制度；均不得用于声称正式防回滚已实现。

## 范围与提交顺序

1. 权威按 `(tenant, view)` 用一个原子事务提交不可复用 command、前版本 CAS、新版本、清单／策略内容摘要和状态，产生可精确核验的提交记录。此点是**权威提交点**，但不是授权可用点。独立见证初始持有同一受控 scope 与 epoch 的受信高水位及摘要。
2. 推荐模型按“权威先提交、见证后确认”顺序。只有经验证的、恰好承接见证当前高水位的权威提交证明，才允许见证原子推进至新版本；见证确认后，双侧均返回新版本及摘要时可查询。任何一个 scope 的权威先于见证期间冻结该 scope 后续发布；查询比较两侧不一致即拒绝，不保留旧许可作为回退。另一个 scope 不因此自动冻结。
3. 两方没有共同事务。权威提交但见证未确认时为 `PENDING_WITNESS`：即使用户未收到成功响应，也不得重新提交业务动作。按命令 ID 对权威、见证进行只读核对；需原始且精确匹配的提交证明、受控恢复流程才可显式推进见证。缺证明、不一致或未完成审批则保持冻结。见证已确认但响应丢失，以两侧只读证据核对，不重复推进。恢复是否需要正式双人审批／谁能操作属于部署决策；本机仅用人工显式调用替身，不冒充审批。
4. 见证领先权威、同版本摘要不同、跨 epoch、未知历史、见证或权威不可读均故障关闭。不得自动降低任一侧高水位、用 TTL 解锁或以空回执证明未提交。整体权威与见证共同回滚或共同被攻陷，在缺少第三独立证据时无法检测。

## 新鲜性与返回前检查

- 每次 T1/T2 各生成新的高熵 nonce；分别验证受信权威和见证的签名、公钥用途、精确 nonce／audience／scope／epoch／版本／摘要和活动状态。响应不能作为下一次查询的权威缓存；T1 与 T2 的一致状态不同则丢弃结果。两个新鲜的读不构成原子跨服务快照；读之间出现变化允许拒绝，T2 后变化不追溯召回。
- nonce 及签名只能阻止旧响应直接重放，**不能证明回答者的状态是最新**。测试模型假定两个读源各自线性一致、签名密钥受控且见证独立不可回退；实际权威与见证是否满足这些假定未选择产品、未验证，须以目标系统协议、访问控制、持久性和故障注入另行证明。
- 由应用校验相同版本／摘要只能在两个读源均可信且足够新的假设下工作；一个或两个被恢复、落后或合谋时不能仅靠签名／nonce保证安全。身份撤权仍须另有权威身份状态源；J1 的短期令牌重放边界不变。

## 本机测试与正式门禁

用各自独立的新建临时 SQLite 和内存生成的 ES256 测试密钥模拟两侧持久状态，测试进程退出点采用显式故障注入／重建对象，不代表真实宕机或共识。覆盖权威先提交、见证未确认、显式证据恢复、提交响应丢失、见证响应丢失、旧回执／版本错配、nonce／签名／scope 错误、不可达、T1/T2 变化、两侧同时回滚的负例。不改变真实策略或网络入口。

真实部署前必须确定见证独立故障域、读一致性和不可回退根；签名与见证的密钥责任人、恢复审批人／双人隔离、完整历史缺失后的新 epoch、见证提交/恢复的授权流程，以及产品和可用性目标。没有这些证据不得将本机结果视为生产防回滚验收。
