用户明确批准仅启动既有 `compose-dev-mysql-1`，使用已有配置凭据读取 information_schema／版本元数据；不新建容器、不拉取镜像、不执行迁移，不读取业务行。

## 实际执行

1. `docker start compose-dev-mysql-1` 恢复既有容器及数据卷；未 compose up、创建容器、拉取或升级镜像。正常数据库启动可能执行恢复写入，已包含于用户本轮明确授权。
2. 从既有容器配置中仅在内存取得 MySQL 凭据，通过标准输入交给 mysql 客户端，不置于命令行参数，不输出或保存秘密。已有凭据认证成功；这只是数据库元数据访问，不是 Runtime JWT 管理员身份。
3. 两个会话均显式 `SET SESSION TRANSACTION READ ONLY` 与 `START TRANSACTION READ ONLY`，仅查询服务器版本、指定库／表／列元数据及 Alembic 运维版本，再 COMMIT；未 SELECT Run、事件、主体、输入、回执或评分业务行。
4. MySQL 按授权保留运行；没有启停其他已有依赖、Runtime 或 Worker。未运行 dev_stack.py 或 Runtime lifespan。

## 启动与后续门禁

- 不以 `RUNTIME_MIGRATE_ON_START=false` 绕过 schema 不足直接启动；关闭迁移不会补齐缺失的证据表。
- 不运行默认启动或 dev_stack.py：当前仓库启动路径可能将 0005 库迁移到后续版本，也可能启动 Worker／节点组件，均超出本轮授权。
- 优先由用户指定另一个**已有且满足 schema 的非生产 Runtime 账本／实例**；不创建替代空库或把临时测试库当成真实账本。
- 若需要升级当前既有开发库，需另行批准迁移范围，并先核对 0006～0011 影响、已有数据兼容、备份／恢复与停机边界；本轮未迁移，也未擅自创建备份资源或执行恢复。
- 真实验签管理员令牌、issuer／audience／JWKS 可用性、单个 Agent ID 和带时区最长七天时间窗仍待确认。配置中的 Keycloak realm／角色不是已有令牌证明，不用 MySQL root 替代 Runtime 管理员。
- 用户禁止业务明细读取，因此不从 t_run 中枚举 Agent／租户／时间；具体查询范围需用户提供。只读启动仍须明确 api 角色的 Redis／取消订阅与审计落库边界，保持写协议关闭、无 Worker／节点代理／OTLP 导出。
