# S14.1 独立权威与见证：产品选型及恢复方案（待确认）

2026-10-27。本文件是针对候选 A 的设计评估，不是实施批准或真实环境验收。候选 A 的本机状态机已验证；产品、故障域、信任根、人员、成本及真实环境尚未确认。J1 允许有效期内委托断言重放的既定选择不变。

## 一、推荐方案与前提

**推荐首先验证 etcd v3.6 系列作为权威事务引擎；独立见证先开展产品能力与组织边界评估，不预先指定厂商。** 理由：etcd 文档定义了事务比较／原子写入与默认线性一致读取，可作为模型中权威的技术候选；需由应用实现 scope CAS、不可重用命令／回执、清单及策略同事务提交、访问控制和 T1/T2，不能把产品能力等同已实现系统。应禁止面向授权决策使用可能读取旧数据的 serializable 模式。[etcd API](https://etcd.io/docs/v3.6/learning/api/)；[etcd 一致性保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)。

**etcd 本身不是独立防回滚根**：官方恢复文档说明快照恢复可能令客户端观察到较旧版本；revision bump 处理修订及 watcher 缓存，不恢复快照之后丢失的授权内容，不能替代独立见证或重新审批。[etcd 灾难恢复](https://etcd.io/docs/v3.6/op-guide/recovery/)。现阶段不建议把 Kubernetes 控制面已用的 etcd 直接当平台账本：其资源竞争、管理权限和共故障域未评估；此处为设计建议，并未核实当前集群或另建实例。

独立见证候选必须同时满足下列**待证明**能力：
1. 独立于权威的管理员、凭据、存储、备份／恢复与故障域，能保存按 scope／epoch 的防回退高水位、版本和摘要。
2. 对权威提交证明执行受控验证与单调推进；数据面读取拿到经认证的当前高水位，需证明读取的新鲜性和一致性，不能依赖历史签名、客户端本地缓存或旧 receipt。
3. 权威领先／见证领先、双方响应丢失和完整历史缺失时均可安全冻结并由受控流程恢复；记录审计证据，操作人不能单方面清除历史。

优先比较企业已有的独立受管高水位／见证服务；如果企业允许外部云，Azure confidential ledger 可作**待评估的防篡改历史与回执候选**，其官方说明提供追加式账本和交易证明，但尚未据此证明满足本项目的当前高水位线性一致读、scope CAS、nonce 绑定、跨服务提交协议或隔离职责，也未确认地域、可用性、成本和采购许可。[Azure confidential ledger 概述](https://learn.microsoft.com/en-us/azure/confidential-ledger/overview)。若不能证明全部必要能力，则不能用作正式见证。

对象存储 WORM／S3 Object Lock 可用于保留历史检查点与审计，但受保护对象版本不能删除并不自动证明“最新高水位”或跨服务原子性；不得单独作为实时见证。合规模式留存是强约束，具体保留期限和费用需另行批准。[S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)。

## 二、选型比较与证明缺口

| 组件／产品候选 | 有依据的能力 | 未满足或尚未证明的门禁 | 建议 |
|---|---|---|---|
| etcd 事务权威 | 默认线性一致读、事务 CAS；多数派故障可能不可用 | 运行模式、权限、备份恢复、单 cluster 整体回滚防护与证书治理；不能单靠 revision bump 防旧业务数据 | 首选受控隔离评估；不安装或启动 |
| MySQL 事务权威 | 仓库已有开发配置，可作为事务模型比较 | 未确认运行拓扑／隔离级别／故障切换语义，单库回滚与独立见证仍需解决；未访问任何数据库 | 保留备选，不使用原库 |
| 独立受管线性一致见证 | 若真实服务能证明高水位与隔离根，可满足方向 | 当前无已确认服务、厂商、API、身份或独立治理证明 | 提供候选后做逐条能力验证 |
| Azure confidential ledger | 官方文档描述追加、防篡改及交易证明 | 实时最新状态证明、条件更新／CAS、事务顺序、地区／权限／费用与恢复需验证；不能仅以 inclusion proof 推断最新 | 云环境条件允许时调研，不创建 |
| WORM 对象存储 | 可保护指定对象版本在留存期内不被覆盖／删除 | 不能单独证明最新版本、遗漏检测或两个存储原子性 | 仅作为可选审计／恢复证据 |
| Vault Transit／企业 KMS | Vault Transit 文档提供签名等密钥操作 | 不直接提供不可回退高水位；密钥服务与权限隔离、故障域、可用性未核实 | 作为签名根候选，不视为见证 |

仓库配置包含本机 dev Vault 与 Helm 的 Vault 注入描述；本机 dev 配置是内存态，不是现成生产信任根或运行证据。签名能力参考 [Vault Transit 文档](https://developer.hashicorp.com/vault/docs/secrets/transit)。

## 三、信任根与新鲜性（建议）

- **传输认证**：权威和见证各有独立、受控服务身份和信任锚；查询端通过明确受众与双向认证等经批准的方式访问，禁止开发头。两方证书、签名密钥及管理凭据不得共享；是否使用 mTLS／工作负载身份由安全团队确认。
- **授权发布根**：清单／策略发布绑定提交者、scope、版本、内容摘要和审核证据；签名密钥建议由独立受控 KMS/HSM 或企业 Vault Transit 管理。签名证明来源和内容完整性，不证明该记录是最新的。
- **见证根**：由与权威不同管理责任链持有，验签、轮换、失效、历史证明与恢复必须有明确策略。引导信任根／换根必须得到独立审批并与历史身份连续性绑定；密钥泄露、根不可验证或见证失联时失败关闭。
- **新鲜性**：每次 T1/T2 使用新的 challenge，将 scope、epoch、版本／摘要、受众和 challenge 绑定到受验证的两侧响应；还需证明两侧读取各自具备所需一致性且见证未整体回退。challenge 防旧响应拷贝，不能证明服务未基于旧状态签出新响应。两次读不构成跨服务原子快照，两侧不一致直接拒绝；T2 后完成的撤权不召回已释放数据。
- **防关联风险**：若权威、见证和签名根同处同账号、同管理主体、同备份或同恢复权限，可能一并回退／受控，不能仅靠逻辑分库宣称独立。

## 四、故障域与可用性（建议，尚未实测）

| 范围 | 推荐分离 | 待确认 |
|---|---|---|
| 权威节点 | 有多数派的独立实例／故障域，大小按真实平台与预算设计 | 节点／机房拓扑、网络、时延、RTO／RPO；不预设当前资源 |
| 见证 | 不同的管理与凭据、恢复权、存储和备份域；原则上独立基础设施／账号 | 企业是否已有满足条件服务，跨地域与数据驻留要求 |
| 签名和 trust root | 不与单个账本管理员共享全权，签名授权与恢复分离 | KMS/HSM/Vault 可用性、谁能轮换与吊销 |
| 审计与备份 | 独立受控留存；记录摘要／版本、审批和恢复，不记录用户令牌或数据行 | 留存期限、访问人、加密与清理规则 |

见证作为逐提交同步门槛时，任一方不可用即影响授权发布及读取；不能同时承诺持续可用和严格失败关闭。具体可用性取舍、可接受恢复时间由业务和运维确认。

## 五、提交与恢复审批（建议流程）

既定本机协议为权威先提交、见证确认后可用；权威／见证无共同事务。正式恢复应采用经批准、可审计的操作单：

1. **冻结**受影响 scope 的查询和发布，不使用缓存或旧许可；保全命令、精确回执、epoch、版本、摘要、签名和独立审计记录。
2. **核对**由权威与见证分别提供经过认证的新鲜状态；校验 scope、epoch、版本、摘要、命令及历史连续性。权威领先时只能依据可验证的已提交记录，显式推进见证；见证领先或存在不一致时禁止降低见证或覆盖旧状态。
3. **审批**建议由数据责任人和独立安全责任人两人审批，恢复执行人不自批；涉及见证根、密钥换根、版本重建或新 epoch 时需额外安全审批和运维确认。此为建议，尚无已指定的人员或组织制度。
4. **恢复并复核**在隔离状态验证见证／权威一致性与 T1/T2 失败关闭；完整历史无法证明时保持冻结，拟定新 epoch 和重新审核授权，不从旧备份自动恢复许可。恢复审批不自动授权生产部署或业务数据访问。
5. **解除冻结**仅在双侧新鲜状态、信任根、审批凭证和人工验收齐全后执行；保存操作记录，明确 T2 之后结果不能召回。

灾难恢复若权威和见证共同丢失或共同回滚而不存在更高独立证据，不能通过 hash／签名自行还原真实最新状态；需要另行授权的信任重建和业务重新审批。

## 六、可本机验证与人工确认

**可本机继续验证**：沿用临时 SQLite、内存 ES256 测试密钥、纯替身，补充 etcd 风格 CAS／单事务抽象、见证先后状态、nonce／签名／scope、版本冲突、双侧失联与旧状态负例；验证结果只适用于模型，不能冒充 etcd 或云服务实测。此前模型结果为 230 passed／2 warnings，证据见《2026-10-27-S14候选A权威见证隔离验收报告》。

**需人工确认**：

1. 部署前提：是否允许自托管 etcd，是否存在企业可用的独立见证；是否允许外部云、地域及预算。
2. 安全目标：是否要求抵抗权威整体回滚、权威与见证共同管理员或共同灾难；可接受停用时间与数据恢复目标。
3. 信任根：签名／认证的企业 KMS/HSM 或 Vault、密钥生命周期及信任根持有人；本地 dev Vault 不计入。
4. 故障域与责任：平台运维、见证运维、安全、数据责任人、业务发布人和替补；权限应相互隔离。
5. 恢复审批：双人或其他审批要求、见证补写与换根权限、审计保留、新 epoch 和丢失历史重新授权规则。
6. 真正环境验证另需明确资源、费用、权限、网络和演练授权；以上确认不自动授权真实环境操作。
