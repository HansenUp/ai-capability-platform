## 2. 推荐总体方案（需批准）

**Runtime 权威操作回执＋持久交付 outbox＋Langfuse 不可变评分修订＋读侧在线核验。** Langfuse 继续是评分事实源；Runtime 只承载身份／顺序／幂等／交付证据，不另建一套独立满意度事实库。outbox 暂存发送所需内容仍是新增持久数据，必须明确 ADR-0002 边界、保密和留存后才能实现，不能以“只是技术表”绕过批准。

来源证明链：验签原发起人 → 服务端核对完成 Run 与固定 Trace → 原子登记修订及交付内容摘要 → 认证的 Runtime→Observe 调用 → 受控 Langfuse 写入 → 读回同一 score 并匹配权威回执。来源是受信 Runtime 回执，不是 Langfuse metadata 的布尔值或自报主体。

推荐先采用在线核验，不增加反馈签名密钥。metadata 中的 receipt_id 仅是非可信查询线索；Console 必须用验签用户令牌从 Runtime 按当前租户／Agent cohort 取得权威证据，再逐字段及摘要比对，不允许任意 ID 探测其他租户。若未来要求离线验签，再单独确认签名算法、密钥轮换／撤销与验证方；签名本身也不证明交付完成或不存在更新修订。

Runtime→Observe 仍需独立的服务调用认证与最小权限，不能转发用户 Bearer 给 Langfuse、复用发布管理账号、复用用户 JWT 签名密钥或仅信任来源 IP。认证方式和凭据需要人工批准，本轮不配置。历史评分不自动回填证明、不删除、不提升信任。

## 3. 建议写入／改评契约 v2（需批准）

### 身份、资格与内容

- 仅真实验签用户 JWT 的 Run 原发起人；租户／主体／Agent／版本均取服务端，开发头、服务身份、管理员代评、代理代评默认禁止。
- 建议仅 completed Run 可创建评价；绑定固定完成事件序号与 Trace ID。Trace 缺失、关联冲突或归属无法确认则拒绝，不能在交付时重新选“最新 Trace”。
- 建议第一阶段仅 NUMERIC -1／0／+1，拒绝布尔和小数；0 为明确中性改评，会使该 Run 不再贡献二元分子，不等于删除历史、差评或撤销。是否支持撤回须另定动作，不借用 0。该约束比旧 API 严，需确认兼容方式。
- 推荐首个可信入口不接受 comment／correction，避免新增敏感原文持久化。旧接口既有内容不迁移；如要纳入新协议，需先确认脱敏、加密、留存及摘要泄露风险。

### 幂等与修订

- 逻辑评价键：可信 `(issuer, tenant, run_id, original_subject, user_feedback)`；每 Run 最多一个当前评价，不按 Trace 数投票。
- 请求键采用 UUID attempt_id，绑定服务端主体空间、动作、Run／完成序号、固定 Trace、expected_revision、完整规范化内容摘要及协议版本。同键同内容只返回原回执；同键不同内容返回 409；同键跨主体不可查询或复用。不能靠正文哈希合并不同用户请求。
- 用 Runtime 事务锁／唯一约束串行检查 expected_revision 与主体活动锁；新评价从 0 开始 CAS，改评必须携带已读版本。两标签改评竞争只有一个能取得下一修订，另一个 409 后只读刷新，不自动覆盖／合并。服务端分配单调 revision 与 accepted_at，不按客户端时钟排序。
- 每次有效改评生成新的不可变 score_id，重放同修订必须使用同 ID、name、固定 timestamp 和完整内容；不覆盖上一版 score 来冒充修订历史。交付顺序不能改变修订顺序；迟到旧修订不重新成为最新。
- 同一主体已有未决工作台写则不准入反馈；反馈未决也应冻结同主体全部新写，仍允许只读与重新认证。这需要新增 feedback 动作及 SDK／Console 协议扩展，既有五动作不能直接套用数据库内 COMMITTED 回执。

### 非原子外部写与未知结果

- Runtime 登记／outbox 提交只证明 ACCEPTED／PENDING_DELIVERY，不等于 Langfuse 已成功；网络两端不可能靠一个本地事务实现原子提交。
- 下游已发送但响应丢失、返回异常或暂未查到评分：标 UNKNOWN／PENDING_OBSERVATION，保留活动锁。404、空列表、超时、Run 终态不能证明无效果；不得换新 ID 再写。
- 只有严格匹配租户、主体、attempt、动作、Run／Trace、revision、协议、score_id、固定 timestamp 和规范化内容摘要的服务端读回证据，才能形成 OBSERVED 终结回执；原操作者再显式 ACK 收口，不自动重复业务写。
- 只有确定在任何外部发送前拒绝／回滚且没有可发送 outbox 意图，才能签发 REJECTED_NO_EFFECT。已被发送的请求不能仅因失败响应归为无效果。
- 推荐首轮故障恢复先做只读对账，不启用自主重投。后续若批准 outbox 自动交付／重投，必须先证明固定本机版本对同一完整载荷确实幂等，限定唯一发送者／租约、无新 ID／新时间重试，并明确迟到投递、停机恢复和人工裁决；不是用增加重试绕过一致性缺陷。

### 旧 API 兼容与在途边界

推荐新增独立 v2／workbench feedback 入口；旧 API 暂保留但始终 legacy-unverified，不静默升级历史数据或破坏旧 SDK。旧入口在新 attempt 登记前已准入的请求仍可能完成，不能追溯撤销；它们没有新协议回执，绝不能凭时间接近或正文相同归到新 attempt。旧入口何时禁用／迁移与 Observe 新旧路径隔离需单独批准，不直接把现有 `/feedback` 切为全量新认证。

## 4. 可信读取与指标版本

- 当前 `strict_readonly_unverified` 契约维持不变。未来可信读取必须新增明确指标版本，不能开放 HTTP trusted 开关或悄悄把现有路径构造的 False 改 True。
- 新版本按权威 revision 选择最新已接受修订，再验证其对应 Langfuse 内容与回执；不能用 Langfuse updatedAt、score ID 字典序或网络到达顺序取代业务修订。
- 最新已接受修订尚未观测、内容被改动／缺失或证明不完整时，该 Run 未决，正式比率未知；不能回溯上一个 OBSERVED 点赞。明确无效果拒绝不创建有效修订，也不替代当前评价。
- 最新中性仍不回溯；有效 ±1 每 Run 最多一份，满意度与覆盖率沿用已批准 cohort 口径。混合历史未证明来源时继续报告诊断与完整性不足，不能只挑可信子集冒充整体可信满意度。完整覆盖历史的迁移策略须另行确认。
- 不返回个人排名、评论、correction、令牌或完整证明正文；读回失败不泄露其他租户存在性／数量。北极星仍待定义。
