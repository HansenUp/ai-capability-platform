# 首个垂直切片场景确认纪要

- 日期：2026-10-16
- 状态：场景已确认；业务系统负责人与接口细节待填
- 关联计划项：P0-3.3（实施计划）、A10（Phase 0 收尾清单）、S4 垂直切片
- 关联需求：SC-01
- 关联 ADR：ADR-0007（治理与供给优先）、ADR-0009（授权与范围审批）、ADR-0010（数据分级）、ADR-0011（执行者身份与幂等责任）

## 1. 结论

首个垂直切片场景确认为"工单总结 Agent"，对应实施计划 S4（第 9～10 周）与里程碑 M1。

选择理由：

1. 只读场景，不触发高风险写与幂等改造，适合作为第一个贯通"身份、授权、网关、MCP、观测、评测"全链路的切片。
2. 仓库中已有可复用资产：MCP Server 模板（`mcp-servers/template/`）、示例 Skill（`skills/ticket-summary/`）、快照回放用例（`evals/snapshots/ticket-summary-basic.jsonl`）。
3. 输出是结构化文本，便于用评测数据集度量质量，满足发布评测闸门的前置条件。

## 2. 场景范围

### 2.1 范围内

| 项 | 内容 |
|---|---|
| Agent | 工单总结 Agent（Agent 标识待 S4 配置时定，示例中使用 `ticket-summary`） |
| 能力 | `ticket.search`（按关键字与条件检索工单）、`ticket.get`（按工单号取详情含处理记录），均为只读（`risk_level=read`） |
| 技能 | `skills/ticket-summary` |
| 输出 | 结构化总结卡片，字段沿用 `skills/ticket-summary/references/format.md`：问题、根因、处理过程、客户反馈、可复用经验 |
| 使用者 | 有权限查看对应工单的客服与运营人员；权限以下游业务系统的行级权限为准 |

### 2.2 范围外

- 任何写操作：关闭工单、重开工单、通知客户、写入知识库。本场景的 Agent 不绑定 `ticket.close_batch` 等写工具。
- 跨系统组合（如同时查询客户档案、订单系统）。
- 批量总结与定时汇总报告。
- 总结结果自动入知识库（`skills/ticket-summary/SKILL.md` 中提到的"沉淀"仅指输出可复用经验文本，不自动入库）。

### 2.3 与现有资产的差异（待 S4 处理）

- `skills/ticket-summary/SKILL.md` 当前只声明依赖 `cap.ticket.search`，且步骤 3 描述了写操作的预演与审批。按本纪要范围，S4 需要把依赖补充为 `ticket.search` 与 `ticket.get`，并把写操作步骤移出本场景的 Skill 内容。该调整属于 S4 实现任务，不在本纪要范围内。
- `mcp-servers/template` 的示例工具是 `ticket.search` 与 `ticket.close_batch`，不含 `ticket.get`；`mcp-servers/ticket/` 需基于模板新增。

### 3.2 工具契约

| 工具 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `ticket.search` | `q`（关键字，可空）、`status`（可选）、`created_from` / `created_to`（可选，ISO 8601）、`cursor`（可选）、`limit`（可选） | `items`（工单摘要列表）、`next_cursor`（无更多时为空）、`total`（可选） | 仅返回调用者有权查看的工单 |
| `ticket.get` | `id`（工单号，必填） | 工单详情，含处理记录与客户反馈 | 无权限或不存在时返回统一的未找到或无权限错误，不泄露存在性 |

### 3.3 字段

工单摘要（`ticket.search` 的 `items` 元素）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 工单号，全局唯一 |
| `title` | string | 标题 |
| `status` | string | 状态，枚举值由业务系统提供（待填） |
| `priority` | string | 优先级（可选） |
| `category` | string | 分类（可选） |
| `owner` | string | 当前处理人标识 |
| `created_at` / `updated_at` | string | ISO 8601 时间 |

工单详情（`ticket.get`）在摘要字段基础上增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `description` | string | 问题描述原文 |
| `records` | array | 处理记录，元素含 `time`、`actor`、`type`（如回复、转派、备注）、`content` |
| `customer_feedback` | object | 客户反馈，含 `score`（可选）、`comment`（可选）；无则为空 |
| `closed_at` | string | 关闭时间（未关闭为空） |
| `tenant` | string | 租户标识 |

字段以上述名称为平台侧的规范名，业务系统字段名不同则由 `mcp-servers/ticket` 映射。

### 3.4 分页

- 采用游标分页：请求带 `cursor` 与 `limit`，响应返回 `next_cursor`。
- `limit` 默认 20，上限 50（初始值，与业务系统确认后可调整）。
- `ticket.get` 的处理记录过多时，业务系统可截断并给出 `records_truncated=true`，平台侧不自动翻页拉取全部记录。
- 工具结果超过 `TOOL_RESULT_OFFLOAD_TOKENS` 阈值时，由 Runtime 外置为 `artifact://` 引用，不属于接口约定。

### 3.5 鉴权方式：OBO 令牌

- 调用链：用户 → Runtime → 能力网关 → `mcp-ticket`（MCP Server）→ 工单系统。
- 能力网关通过 Token Exchange 为每次调用换取 OBO（On-Behalf-Of）令牌，令牌的 `sub` 为终端用户，`act` 为执行的 Agent，`aud` 为 `mcp-ticket`（Keycloak realm `ai-platform` 中已存在同名 Client），并带租户信息。
- `mcp-ticket` 通过 JWKS 校验令牌的签名、签发者、受众与有效期，校验失败返回 401。
- 行级权限由工单系统按 `sub` 判定，平台不在 MCP 层重复实现完整鉴权，也不使用共享的服务账号读取全量数据。
- 开发期：令牌验签属于 S8 工作包；S4 阶段 `mcp-ticket` 沿用开发头 `X-AI-Dev-Sub` 指定身份，且仅在 mock 模式或明确的开发配置下启用，真实模式必须校验 OBO 令牌。

### 3.6 数据分级与安全

- 工单内容可能含客户个人信息，数据等级由企业安全合规负责人确认后写入本节：当前等级（留空，待填）。
- 在等级确认前，按"内部"等级处理：仅允许使用已过合规审查的模型，观测记录脱敏（见 ADR-0010）。
- 若确认为"机密"，则本场景只能使用私有化部署模型，并且观测只记元数据，该情形会触发私有化模型部署，需要提前评估。
- 业务系统接口不得返回超出调用者权限的数据；这是 S4 跨用户访问测试的验收对象。

## 4. 本机开发期的 mock 数据源约定

业务系统只读 API 在 S3 末仍可能未到位（风险表已列出），本机开发与 CI 一律使用 mock 数据源，不等待真实接口。

### 4.1 mock 模式

`mcp-servers/ticket` 基于 `mcp-servers/template` 实现，支持两种后端，由环境变量选择：

| 变量 | 取值 | 说明 |
|---|---|---|
| `TICKET_BACKEND` | `mock`（本机默认）/ `http` | 选择数据来源 |
| `TICKET_API_BASE_URL` | URL | 仅 `http` 模式使用，业务系统只读 API 的基地址 |
| `TICKET_API_TIMEOUT_S` | 秒，默认 10 | 仅 `http` 模式使用，请求超时 |

以上变量为本纪要约定，由 S4.2 实现时读取，并在实现后同步到根目录 `.env.example`（当前已先行列出）。

### 4.2 mock 数据要求

- 全部为虚构数据，禁止使用真实客户的工单内容、姓名、联系方式。
- 数量不少于 30 条，兼作 S4.6 评测数据集的素材来源。
- 覆盖：多种状态；处理记录多条的工单；有与无客户反馈；超长文本（可触发结果外置）；空结果查询；分页（超过一页）。
- 包含至少两个不同处理人（`owner`）与两个租户的工单，用于"跨用户访问、跨租户访问"测试：调用者只能读到自己有权查看的工单。
- 存放位置：`mcp-servers/ticket/` 内的数据文件，随代码入库，目录由 S4.2 实现时确定。

### 4.3 与真实接口的切换方式

1. mock 与真实后端实现同一内部接口，返回同一数据模型；MCP 工具名、入参、出参不随后端变化，Agent 配置与 Skill 不需要修改。
2. 切换只改环境变量：`TICKET_BACKEND=http`，并设置 `TICKET_API_BASE_URL`。不改代码、不重新发布 Agent 版本。
3. 切换前必须通过契约一致性测试：同一组用例分别对 mock 与业务系统的测试环境各跑一次，字段、分页、错误码的结果结构一致。
4. 切换前必须确认第 3.1 节责任人已填、第 3.6 节数据等级已确认、OBO 令牌验签已生效（S8 工作包完成，或有等价的临时方案并经架构师确认）。
5. 切换后重跑快照回放与评测数据集，对比 mock 阶段的结果；差异需说明原因后才允许进入预发布。

## 5. Phase 1 验收口径

本场景的验收以 `docs/plan/实施计划.md` 的 S4 出口标准（M1 验收）为准，不另设口径，原文如下：

> 工单总结 Agent 生产可用；Trace / 审计 / 灰度可用；不变量与快照测试在 CI 通过；最小安全闭环与数据分级矩阵通过跨用户访问、附件越权、非白名单工具、机密数据外发四类测试；业务方签字。

结合本机开发的口径（`docs/plan/Phase0收尾与Phase1本机开发计划.md` 第 4 节）：

| 项 | 本机阶段判定 | 需要真实环境才能闭环 |
|---|---|---|
| 工具链路 | `ticket.search` / `ticket.get` 经能力网关分发到 `mcp-ticket`（mock 后端），Run 事件日志完整（S4.2、S4.3） | 接入业务系统真实只读接口 |
| 快照与不变量 | `evals/snapshots/` 不少于 5 条工单总结快照，快照与不变量测试在 CI 通过（S4.5、S4.4） | 无 |
| 评测 | Langfuse 中 `ticket-summary` 数据集不少于 30 条，发布评测闸门读取其结果（S4.6）；评测通过阈值（留空，待产品负责人与架构师在 S4.6 前确认） | 用真实工单抽样复测 |
| 安全 | 跨用户访问、附件越权、非白名单工具、机密数据外发四类测试通过（S4.8、S4.9） | 渗透与安全评审 |
| 可观测 | Trace、审计、灰度可用 | 生产环境确认 |
| 投产 | 预发布就绪（Helm values 与镜像齐备，S4.7） | 预发布 → 生产部署、业务方签字 |

关于 S4.10（幂等责任确认）：该项针对高风险写工具。本场景为只读，没有写工具，按"不适用"处理；但计划任务定义不在本纪要内修改，是否在计划中标注由架构师经计划变更流程确认。
