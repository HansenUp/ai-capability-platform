# S12.1 0005 → 0011 迁移评估与隔离演练

## 结论与授权边界

**临时 MySQL／SQLite 的合成结构演练通过；现有 `ai_platform` 仍为 0005，未迁移。** 本轮不构成现有库升级、真实数据备份、管理员身份配置或真实可信反馈来源验收授权。

现有库只读取版本、表名、引擎、字符集／排序规则及 SQL 模式元数据，不读业务明细。所有 DDL、合成数据、dump／restore 和故障注入仅作用于唯一命名的临时库；不新建账号、不写 Langfuse 评分／Trace，不启动真实 Runtime／Worker，不部署生产，自动跟进保持暂停。

## 迁移变更与兼容性

| 迁移 | 结构变更 | 兼容／回滚要求 |
|---|---|---|
| 0006 | 新建 t_node_model_route、t_node_command_receipt | 不修改旧 Run／事件；降级删除节点路由和指令回执 |
| 0007 | 新建 t_workbench_scope、t_workbench_attempt 及 scope 索引 | 首次建立主体锁／写前登记；降级会删除活动锁及未决证明，不能当作安全解锁 |
| 0008 | attempt 增 action（非空、默认 credential）、call_id、params_hash | 已有 0007 行补为 credential；降级会丢动作／审批绑定，不能继续安全处理新动作 |
| 0009 | attempt 增可空 value_hmac | 不回填原始回答；降级丢回答绑定证据 |
| 0010 | attempt 增五个可空 create_* 绑定字段 | 旧行保持 NULL；降级丢创建范围／快照绑定 |
| 0011 | 新建 t_feedback_outbox，唯一键 (run_id, score_revision) | 不把旧评分回填为可信；降级删除交付意图／观测摘要，可能丢失外部未知效果的恢复依据 |

源码审查确认 0006～0011 没有修改旧 t_run、事件、输入、凭据、工具操作、Agent 或审计表，也没有调用外部服务。新增表无历史数据回填；schema 升级不意味着历史评分获得来源证明。

旧数据演练覆盖 7 张 Runtime 旧表：已完成 Run、带 owner／epoch／过期时间的 working 租约 Run、微秒时间、JSON 扩展、SQL NULL／非空 Skill 锁、事件、合成二进制凭据及工具操作。前后逐表数据摘要、行数、列类型／可空性和索引名称一致。二进制样例不是可用真实凭据，未测试真实解密或业务执行。

额外在 0007 插入合成 PREPARED 行，验证 0008 默认 credential、其余新增字段 NULL；0011 唯一键元数据存在，重复升级到 0011 不改变状态。新 workbench.created_at 的 MySQL DateTime 精度不能默认等同旧 Run 的 DATETIME(6)，修订仍以服务端 revision 为准；本轮没有改动历史迁移或时间契约。

## 真实环境的元数据发现

- MySQL 8.4.9，ai_platform 为 utf8mb4／utf8mb4_0900_ai_ci；当前表均 InnoDB，启用严格 SQL 模式。临时 MySQL 在同一既有服务器创建 utf8mb4 库，不拉取新镜像。
- ai_platform 不仅有 Runtime 表，还包含 Console 表及独立 alembic_version_console。**未来备份／停写必须覆盖共享库的 Console 写入者，不能只备份 Runtime 七张表或只停止 Worker。** 本轮未读取 Console 业务内容或更改其版本。
- 本次新增五张表在当前真实元数据清单中不存在；当前 Runtime 版本为 0005。演练前后现有版本／表清单一致；这只是结构核对，不是对真实业务内容作校验和，也没有读取真实数据估算规模。

## 临时演练与故障恢复证据

使用四个随机前缀 `s12_rehearsal_*` 库，建立由迁移生成的 0005 合成结构，而非复制真实数据；每次连接核对目标库名，DDL／恢复目标只接受本次精确名称列表，禁止 ai_platform。

1. 0005 合成数据备份：mysqldump 单事务、无表锁／表空间／GTID 注入；合成文件设 0600，校验摘要，从文件恢复到第二临时库，核对 0005 版本及旧数据／结构。
2. 升级到 0011，验证旧数据不变、新字段／索引／约束，并验证 clean head 再升级为空操作。
3. 0011 合成备份恢复到第三临时库，核对 0011 版本、旧数据及新表合成活动 scope／attempt／outbox 不丢失。它们仅是迁移结构样例，不是 Runtime 验签来源样本，也未投递评分。
4. 在临时库降级回 0005：旧表摘要保持，但新表及其中 PREPARED／outbox 数据消失；再升级结构可重建，**已删除的新证明不能由重建表恢复**。
5. 在第四临时库升级 0007 时，故意于创建第二张表前中断。事务 rollback 后已创建的 scope 表仍存在，attempt 表缺失，版本停在 0006。证明 MySQL 多语句 DDL 迁移不能依赖事务整体回滚；单条原子 DDL 不等于整条迁移链原子。
6. 未盲目重试或 stamp 跳过半迁移；仅删除重建这个临时故障库，再从 0005 合成备份恢复并核对版本／数据。该破坏性动作严格限临时库，不是对现有库的恢复授权。

最终正式 MySQL 演练断言 runtime.main 和 runtime.worker.worker 未加载，未启动应用／Worker。所有临时库和合成 SQL 文件均已删除，保留脱敏结果、摘要与日志；不存在已为真实库做好的可用备份。

3. 真实备份会读取敏感业务数据，需单独明确访问、加密存放位置、权限、保留期限与销毁策略。完整覆盖 ai_platform（含 Console、两套版本表）及必要视图／触发器／过程／事件定义；密钥配置按独立安全流程保护，不在报告或 SQL 日志输出。
4. 全 InnoDB 可使用一致性逻辑备份，但备份期间不得并发 DDL；不能把直接复制运行中的 Docker volume 当作已验证一致性备份。若需跨库／PITR，应另外明确 binlog／GTID 与权限范围。

6. 经批准后才由单一迁移执行者进行迁移；Runtime 官方迁移入口有 MySQL GET_LOCK 串行化机制，但它不能替代停写或阻止绕过该锁的外部 DDL。启动迁移关闭，Worker／写协议／节点代理／OTLP 导出保持关闭；只读接口仍须真实验签管理员和已确认范围。

## 回滚分界

- **升级失败、尚未恢复业务写**：保持冻结，记录实际 schema／版本／错误和恢复点；不得自动重跑 CREATE／ALTER、跳版本或打开 Worker。先在隔离恢复库验证，再按另行批准的恢复方案处理，不能自动 DROP 现有库。
- **完整升级且确认没有任何升级后写入**：可评估恢复升级前一致性备份或审核过的降级；需要证明冻结期间没有共享库写入，不是仅凭“反馈还没发送”。
- **已经产生新 attempt／scope／outbox 或外部未知结果**：禁止把 downgrade 0005 或恢复旧快照当作安全回滚，会丢锁／证明并产生重复业务风险。保持停写并保全 0011 完整状态，另行授权只读对账／人工裁决。旧应用若忽略新锁，也不能恢复写入；不提供 TTL 或管理员代解锁绕过。
