## 2. 联调发现

- 本机 realm 导入时显式给出了 clientScopes，Keycloak 不再自动创建内置作用域，令牌里缺 `sub`、角色等声明。改为在 `ai-runtime` 作用域里显式配置全部所需 mapper（D37）。
- LiteLLM 开启了 Redis 响应缓存：完全相同的请求直接回放首次响应，用量也是首次的（命中 0），厂商侧的 Prompt Cache 被掩盖。验证脚本改为固定前缀、问题末尾带序号。生产是否保留网关响应缓存见遗留 3。
- DeepSeek 的前缀缓存在首次请求后十余秒内建立；之后同一前缀命中率约 95%（2428 输入命中 2304）。

## 3. 代码评审

提交前做了一次独立代码评审，报出 12 项（高 1、中高 1、中 4、中低 1、低 5）。已修复并补回归测试的 9 项：

- 应用令牌或 Run 发起人可以审批自己挂起的高风险调用：强制鉴权时只有人员令牌能审批 / 拒绝，且不能是该 Run 的发起人（D46）；
- JWKS 过期刷新不限频，IdP 宕机时每个请求都排队等一次超时：过期刷新同样受最小间隔限制，失败沿用旧公钥；
- 生产基线漏查数据库：`RUNTIME_ENV=prod` 时 DATABASE_URL 必须经 Vault / 文件注入且不是 SQLite；
- 续跑以续跑者身份执行：改为以 Run 发起人身份续跑，续跑者记在请求审计中；
- 令牌头 alg / kid 非字符串导致 500：改为 401；JWKS 返回体异常不再抛出未捕获异常；
- 仅凭用户名前缀 `service-account-` 判定应用令牌：只认 `client_id` 声明；
- 审计 detail 中路径与认证失败原因不截断：截断到 256 字符；
- Settings 的 repr 含密钥：密钥字段 `repr=False`；claude-sdk 子进程再置空 `*_FILE` 路径变量；
- 审计模块说明与实现不符（tool.decision 未镜像）：改正说明，判定结论见执行 Trace 的 execute_tool span。

其余未修或部分修复的项转入下表（遗留 2、8～12）。
