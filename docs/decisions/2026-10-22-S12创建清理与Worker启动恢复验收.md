# S12 创建清理与 Worker 启动恢复验收

日期：2026-10-22。用户本轮明确授权排查并修复前轮全仓的创建清理 CAS 竞争及 Worker 队列断言失败。仅本机开发和临时库／工具替身验证；不启用自动跟进，不部署，不操作真实业务或账号，不提交代码。

## 1. 根因与一致性边界

1. 创建夹具直接读取 Run 并 CAS 迁移 canceled，与会话 Worker 同时写。前轮证据清理读取 submitted／seq=1 后，Worker 已提交 working／seq=3，CAS 正确抛 SeqConflict；不能吞掉冲突、覆盖新状态或靠重试清理。
2. InMemory Worker 先创建消费／周期任务，再 await 启动 reaper。扫描与消费并行，恢复扫描能在消费完成后追加之前读取到的可执行 Run；因此仅观察 Run completed／无租约，并不表示启动恢复完成、队列已消费或 Worker 在途任务已结束。共享测试库还有其他测试的可恢复 Run，局部 Run 终态不能作为全队列退出屏障。

契约：单进程启动恢复完成后才启消费／周期任务；取消尚在启动恢复中的 Worker 不得遗留消费者。测试清理先阻止本 Worker 新领取，再等已领取任务真正退出，之后读取／终结仅本测试所建 Run，最后恢复原暂停状态。终态、租约释放、投递消费和任务 idle 是不同事实，不用一个代替另一个；生产终态／租约原子提交规则及 CAS 保护不变。

## 2. 最小修复

- `worker.py` 将 InMemory 的启动恢复 await 移至创建消费／周期任务之前；Redis 消费与接管路径不改，既有恢复故障日志和周期恢复语义保留。
- 创建夹具提取 `retire_create_runs`：暂停领取 → `idle.wait()` → 原事务清理和候选排除断言 → finally 恢复原 paused 值。未删除共享库其他 Run，也不改业务写 API 或账本语义。
- InMemory 原用例在原有五秒预算内同时等待原 completed／无租约条件、Worker idle 和队列空，再退出 Worker；原 `assert len(q)==0` 保留。新增的是退出条件，不是减少检查或延长时间，也不重执行业务写。
- 新增事件屏障覆盖恢复先于消费、启动恢复时取消、清理等待真实在途 Worker 完成，以及原暂停／未暂停状态均正确恢复。没有新增 sleep 时长阈值，`sleep(0)` 仅让出事件循环以执行已排队任务。
