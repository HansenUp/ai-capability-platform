## 根因证据链

1. 原全仓失败位于 `test_input_while_lease_held_is_redelivered_on_release` 的开头 `_agent()`／`s.commit()`，尚未进入该用例的租约／输入交错。只运行该用例通过，相邻 S7 输入／评审模块也可通过，说明不能把用例名称当成锁持有者。
2. 通过临时、无 SQL 参数的诊断记录观察数据库任务来源：存在 Worker 释放租约与心跳 SQL 被取消的路径。带逐语句栈采集的全仓诊断在另一项 `test_worker_autoclaims_orphaned_message` 的 5 秒条件等待失败（848 passed／9 skipped），但未直接捕获原先那次锁持有者；诊断增加了开销，不能把这次超时当作原锁冲突的直接证明，也未修改其阈值。
3. 检查本机 SQLAlchemy aiosqlite 适配器：执行原生 cursor 后先等待 execute／fetchall，再关闭 cursor；取消可能发生在关闭前。连接会被失效／关闭，但异常、任务或其他引用仍可保留原生 cursor。
4. 独立 SQLite 探针确认：SELECT 具有未消费行、cursor 被保留时，仅 `connection.close()` 并不保证释放其读锁；另一连接 INSERT 已执行，但 commit 报 `database is locked`。故“连接对象已关闭”不能替代“活跃语句已终结”。
5. 新增确定性异步回归：先存两行，让真实 SQLAlchemy／aiosqlite SELECT 完成原生 execute 后停在 Event 屏障；保留 cursor 强引用，再取消读取任务。使用独立 `timeout=0` 写探针，原实现必定在 commit 报相同锁错误（`red.log`：1 failed，1.86 秒）。不依赖随机睡眠、全仓负载、GC 或放大等待窗口。

因此可确定并修复的机制是：**取消读取后未显式关闭、仍被引用的原生 SQLite cursor 能在连接关闭后继续持有读锁，阻塞后续无关写提交**。原历史日志没有原生 cursor ID，不能追溯断言当时必然是某一条具体 Run／心跳查询；本轮通过与症状一致的确定性故障注入和资源级断言验证该机制，不伪造历史锁持有者。

本机核对版本：Python 3.12.0、SQLite 3.42.0、SQLAlchemy 2.0.52、aiosqlite 0.22.1；未安装或升级依赖，不宣称已验证全部 SQLite／驱动版本。

## 最小修复与一致性契约

仅在 Runtime `db.make_engine` 的 SQLite 分支设置标准 sqlite3 connection factory；MySQL 的连接参数与原有 pool_pre_ping／pool_recycle 不变。

私有连接子类弱引用登记由 SQLAlchemy 驱动创建的原生 cursor。连接退出时先显式 `cursor.close()` 终结仍存在的语句，再关闭原生连接；重复 close 幂等。即使取消异常或任务仍强引用 cursor，也不再依赖其 GC 时机释放读锁。弱引用登记不延长正常 cursor 生命周期，默认调用与自定义 Cursor 子类均有验证。

- 活跃连接的读锁仍有效，不在每次读取后强制解锁，不改变未提交事务的隔离与提交边界。
- 连接真正退出时才回收关联资源；不将半提交状态视为成功、不吞掉 commit 错误、不自动重放写请求。
- 没有修改 busy_timeout、连接超时、重试、sleep、WAL／journal mode、隔离级别、连接池、测试阈值或跳过条件。
- `timeout=0` 只用于新增独立写探针，令资源泄漏立即失败，比默认等待更严格，未应用到产品引擎或既有测试。
- 产品实现不 monkeypatch 第三方库、不复制其执行器、不增加全局串行锁；测试的可恢复屏障仅用于控制取消时点。未扩展到 Console 自有数据库或外部 MySQL 运维变更。

## 新增验证

| 用例 | 严格检查点 |
|---|---|
| 取消真实异步 SELECT | 保留 cursor 强引用，取消真实读取后，另一连接立即提交成功；直接访问被保留的原生 cursor，精确断言 `closed cursor`，不是仅检查 aiosqlite 连接已关闭 |
| 活跃读锁与退出回收 | 连接仍活跃时写探针 commit 必须报锁冲突；明确 rollback 后关闭 reader，再开启新的写事务立即提交，最终数据精确为 1／2／4，不包含失败事务中的 3；重复 close 正常 |
| 弱引用与自定义工厂 | 保留自定义 Cursor 子类；无外部引用时可回收，不被登记表持有；已关闭 cursor 与连接重复关闭正常 |

测试编写期间最初附加的 aiosqlite `fetchone()` 异常类型假设不准确：连接关闭时该包装器先报 ValueError，不能直接证明原生 cursor 已关闭。最终改为更精确的原生 `closed cursor` 断言；核心“写探针立即 commit”断言未放宽，红证据仍是在此 commit 的锁错误。默认 factory 调用及重载签名的局部实现问题亦已修正；最终类型检查通过，不以这些调试失败冒充根因证据。
