# S14.1 独立可信权威账本候选与故障恢复矩阵（草案）

状态：A1 的独立权威方向已获用户同意；具体产品、信任根、责任和恢复机制尚未批准。本文仅供选择和后续离线建模，不授权创建服务、读取密钥、连接真实数据或部署。版本／授权数据与经营数据分离；本机 SQLite 账本继续仅作隔离实验，不作为正式权威。

## 1. 安全目标及已知边界

- 按 `(tenant, view_id)` 取得同一权威提交点下的清单、策略、各自版本与关联摘要；成功的撤权／重授权必须形成不可重用的新版本。发布请求以预期版本 CAS 与唯一命令登记，未知结果只读查回执，不自动重放。
- Data Hub T1／T2 对请求绑定身份、租户、视图、列／过滤和清单／策略版本；任一核对不一致、权威不可达或无法证明新鲜性则拒绝，T2 后已释放结果不追溯召回。J1 已选择委托断言有效期内可重放，不得将其误称为权限版本新鲜性。
- 需明确对手模型：应抵抗客户端旧缓存、网络重放、单节点落后以及普通备份回滚；同时记录权威多数派、签名人或独立见证被攻陷／合谋时可能无法检测。线性一致本身不阻止管理员恢复整个集群到旧状态；签名、nonce、时钟、普通多副本或 hash 链本身也不能证明没有整组回滚。

|---|---|---|---|---|

## 3. 推荐新鲜性协议：必须成立的条件

1. **查询请求绑定**：网关／Data Hub 对每次权威读取生成高熵一次性 challenge，在本请求生命周期内不可复用；认证响应必须绑定 challenge、受众／调用方、作用域 `(tenant, view_id)`、权威 epoch、单调提交位置、清单与策略版本／摘要和结果状态。密钥、签名算法、编码／规范化和完整性由可信根约束。challenge 防止复制旧响应，并不阻止持有有效密钥但状态落后的服务对新 challenge 签旧值。
2. **权威读保障**：实际响应必须来自经过鉴权的线性一致读取，或有经审计验证的等效协议；证据要说明读取位置不早于该请求开始前已完成的写。允许 follower 回答的条件必须明确证明同等保证，不能以短 TTL、JWT exp 或本地时钟替代。
3. **独立见证**：若威胁模型包括整个权威恢复旧快照，需不可与权威同时回滚的独立见证确认 epoch／位置／摘要。仅有 checkpoint 不够：它的发布与恢复顺序、耐久提交、查询时新鲜读取、无遗漏和两侧不一致的处置必须明确；如果不能证明见证读取足够新，失败关闭。权威和见证没有共同事务时不能直接声称原子性。
4. **一致快照与结果释放**：权威给出的清单／策略与版本绑定必须是同一逻辑提交点；T1/T2 分别读取并验证。T1 后任何版本变化、epoch 变化或认证失败，T2 丢弃结果；T2 后的撤权不召回已释放数据。用户即时撤权另需权威身份状态源。
5. **安全故障语义**：响应超时、nonce 不符、未知 key、签名无效、旧 epoch、版本／摘要冲突、见证超前／滞后、证明不可验证均拒绝；缓存不得降级为权威。全局断言重放保护与授权状态新鲜性是不同问题。

以上是目标协议，不是当前已实现能力。对“线性一致读＋独立见证的新鲜性”的证明须依具体产品设计和故障注入给出，不能仅凭测试替身断言。

## 4. 信任根、职责与权限（推荐分离，人员待指定）

| 职责 | 推荐权限和约束 | 待确认 |
|---|---|---|
| 数据所有者 | 审核数据集、租户行标签、视图语义及列遮盖；不单独批准自身变更 | 每个视图的业务责任人及接替人 |
| 清单／策略提交者 | 创建具唯一命令 ID 的候选；不持有单人放行或见证重置权 | 发布账号类型、最小权限和来源认证 |
| 独立审核人 | 推荐至少两名不同审核人，均不得是提交者；批准清单、策略和版本摘要 | 人数、角色及组织隔离；S14 本机双审核声明并非真实审批 |
| 权威运维 | 日常成员管理、备份与恢复执行，不得单独改变见证高水位或签名根 | 职责归属、值班和操作审计 |
| 安全／密钥责任人 | 审批签名根、见证身份、密钥轮换及撤销；推荐密钥由受控密钥服务保护 | 具体信任根、托管、轮换、吊销与丢失恢复 |
| 恢复审批人 | 推荐数据责任人 + 独立安全责任人双人批准；执行者不能自批 | 审批人、紧急例外流程、权限和时效 |
| 查询服务 | 只读权威与见证；不可更新版本、重置高水位或选择信任根 | 身份认证方式与网络边界 |

双人规则是本草案建议，非已确认组织制度；实际人员、访问权限和责任主体均未指定。审批不得依赖请求自报身份，操作和证明日志避免记录原始用户令牌和业务行。

## 5. 故障恢复矩阵

| 场景 | 检测／即时行为 | 恢复前提及审批 | 可本机验证与限制 |
|---|---|---|---|
| 权威不可达／无多数派 | 查询与发布失败关闭，不读旧缓存放行 | 权威运维恢复；涉及成员变更按已批准方案执行 | 可用替身模拟不可达；不能证明真实多数派 |
| 写前故障 | 无提交证明则状态未知；只读查命令回执，不能凭缺失立即断定未提交 | 由原发布者／受控流程核对权威最新状态；不自动重放 | 可注入写前故障；“空回执最终可判定”的边界需协议支持 |
| 已提交但响应丢失 | 通过认证的线性一致回执查精确命令／作用域／版本／摘要；不重发原写 | 若权威不可达保持未知，恢复后重新只读核对 | 可模拟响应丢失与匹配，不能证明真实线性一致 |
| 权威领先见证 | 两者不一致，查询与发布冻结 | 按已审核且可证明的提交协议核对并完成恢复；禁止人为把见证提升到未经核验的值 | 可枚举模型状态；不证明协议实现真实原子 |
| 见证领先权威 | 拒绝旧数据及旧授权，禁止降低见证 | 从可验证历史恢复；无完整历史则新 epoch 与重新授权经双人审批 | 可做旧快照负例；不可推断真实见证可信 |
| 权威旧快照／整集群回滚 | 见证高水位或 epoch 不匹配时拒绝；若见证也回滚且无外部根则不可检测 | 停止读写，安全与数据责任人核验权威／独立见证；禁止重设水位掩盖差异 | 可模拟两侧不一致及共同回滚负例 |
| 见证不可达或回滚 | 无新鲜证明即拒绝；不可用缓存冒充 | 恢复独立见证及其可信状态；涉及重置需双人审批与外部证据 | 可模拟失联／回滚；不证明真实独立性 |
| 权威／见证均丢失 | 保持隔离，不接受旧授权 | 需灾备证据、独立安全与数据责任人审批恢复信任根；无足够证据则新 epoch、重新审核／授权 | 可模拟 fail closed；不可推导真实历史 |
| 签名 key 泄露／失效 | 拒绝未知、撤销或不可信签名；旧 key 的历史证据需分界 | 密钥责任人撤销／轮换，安全审核受影响区间；信任根更换需独立审批 | 测试临时密钥／拒绝；不接真实密钥 |
| 清单／策略不同步、T1→T2 撤权 | 比较提交点／摘要；发生变化丢弃旧结果 | 重新发起正常查询；不能自动恢复旧授权 | 已有隔离测试，可补造异常和延迟 |
| 进程崩溃／本机 SQLite 跨进程冲突 | 本地零等待失败关闭；提交前回滚、提交后按权威回执确认 | 查询临时账本不具正式授权效力，人工定位不可用原因 | 仅验证本机进程退出；不代表断电或多节点 |

## 6. 可直接执行与需人工确认

**可直接执行**：用纯内存／临时库、测试密钥和可控替身验证 nonce／受众／作用域绑定、版本／摘要不一致、乱序旧响应、权威与见证任一不可达、写前／写后崩溃、响应丢失及精确回执；保留“新 challenge 仍可能获得旧响应”和“两侧一起回滚无法检测”的负例。此类验证不需要真实服务，可验证客户端失败关闭及协议状态机，不能证明部署安全。具体执行前应依据最终选择冻结状态机，而不是把替身实现当成已选产品。

**需人工确认**：A/B 的具体系统与提交协议；威胁模型、可接受不可用时间和是否同步见证每次提交；责任人与双人审批规则；签名／见证信任根和密钥运维；旧历史缺失时新 epoch 与重新审批流程；目标环境、网络权限、付费／持久资源及生产演练授权。确认这些事项不自动授权安装、创建真实资源或部署。

## 7. 推荐决策顺序

1. 指定威胁模型、数据和安全责任人；决定是否必须检测整个权威恢复旧快照。
2. 比较候选 A 与 B 的可用基础设施和提交／见证协议；若选 A，先冻结同步见证和权威／见证不一致的处理语义。
3. 审批信任根、密钥／见证操作分离、恢复与新 epoch 审批；先做纯替身状态机和负例验证。
4. 如需真实资源，再单独批准环境、权限与演练计划；之后才讨论正式验收与部署。
