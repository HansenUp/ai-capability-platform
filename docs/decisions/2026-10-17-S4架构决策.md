## 2. 联调发现

- Keycloak 26.0 不支持标准 Token Exchange（V2），升级到 26.3；V2 要求终端用户令牌的受众包含请求方（`ai-runtime` 作用域增加 capability-gateway 受众），目标受众由请求方客户端的作用域提供（`mcp-ticket-audience`）。
- 评测与 S3 灰度规则结合：首个版本以 0% + 评测白名单发布，评测通过后放量，避免"未评测的版本先对外可见"。
- 端到端评测发现两个问题并已修复：① 外置的大工具结果经 `read_artifact` 读回时又被外置，模型永远读不到原文、反复读取直到轮数耗尽（回答为空）——read_artifact 的结果不再外置；② LiteLLM 响应缓存回放了其他 Run 的工具调用（D70）。另外模型有时省略 `artifact://` 前缀，引用格式放宽为同时接受裸 32 位 id。
- 评测结果：修复后两次完整评测分别通过 28/30（93%）与 30/30，闸门放行；模型回答有波动，偶发未通过项为能力缺口（`ticket.search` 不支持按负责人筛选，"我负责的工单"可能无法直接列出）与措辞差异（评测规则已补同义词）。
- 独立代码评审：必须修 5 项均已修复并补测试——① 只读工具经网关失败误走"结果未知 / 对账"路径（改为工具错误、Run 继续），影响预演失败不再中断；② 0% 预发布版本可借回滚绕过评测闸门（Console 与 Runtime 都拒绝回滚到 0% 版本）；③ 生产基线未要求 `TOOL_DISPATCH=gateway`（开发执行器只返回模拟结果）；④ 网关登记接口未鉴权，可把 OBO 令牌导向任意端点（启用 OBO 后登记需 `GATEWAY_ADMIN_TOKEN`，`GATEWAY_ENV=prod` 缺少 Keycloak 或管理令牌拒绝启动）；⑤ close_batch 影响预演经网关必然 422（dry_run 不再要求幂等键）。另外评测通过率为 nan 时视为未通过。
- 二次独立评审（安全 + 正确性）：必须修 6 项均已修复并补测试——① 指定版本可绕过 0% 预发布白名单（非续跑指定 0% 版本须在白名单内，否则与不存在同样 404；选版与指定版本共用 `rollout.in_allowlist`）；② 评测脚本不固定、不核对被测版本，闸门可能以旧版本成绩放行新版本（请求固定 agent_version，逐条按 run_id 核对实际版本，不一致计不通过并记入运行 metadata）；③ 写工具经网关遇业务系统 5xx 或缺状态码被当成确定失败（改走"结果未知 / 对账"，4xx 仍作工具错误，只读工具不变）；④ verify-s4 的"非白名单工具"检查恒真（改为断言组装出的工具不含 close_batch，并在网关把 close_batch 登记为 ticket-summary 的核心工具后再次断言；跨用户检查收紧为 404）；⑤ 快照回放含自我比较、快照手写且与真实契约不符（`evals/record_snapshots.py` 经真实 Runtime + 网关 + mcp-ticket 录制 8 条快照，逐条校验 model.request 的 messages_hash 可由日志重建；夜间任务增加重录漂移检查）；⑥ 暴露给模型的 `ticket.search` 入参缺 created_from / created_to（网关种子与 Runtime 本地定义补齐，close_batch 补 ids schema，测试断言与 MCP 工具定义一致）。
