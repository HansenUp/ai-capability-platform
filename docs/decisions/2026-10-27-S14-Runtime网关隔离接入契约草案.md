# S14.1 Runtime／网关隔离接入契约草案（待确认）

状态：供审阅的推荐方案，尚未批准实现或开通接口。范围只涉及受控视图只读查询；不授权真实数据、原库、IdP、服务凭据、外部存储、生产部署或权限扩张。此前签名测试身份是合成样例，不能证明正式身份来源。

## 1. 已有证据与差距

1. Runtime `gateway_client` 服务态传服务令牌和内存用户令牌；网关 `require_runtime_client` 在配置 Keycloak 时验证调用服务并在存在用户令牌时验证用户。用户受众配置可空，开发态可使用未验签声明／头；二者均不能作为新数据接口默认信任。`auth.Caller.principal()` 在正式模式要求终端用户，但仅凭此不等于已满足下面更严格的用途、受众和租户契约。
2. 网关 `/invoke` 查租户能力、做 `invoke` 判定并向连接器换取 OBO；`act` 断言声明用户、Agent、调用服务、Run／call、OBO 哈希和有效期。签发并不证明接收端已实现验证。OBO 缓存按用户令牌摘要／受众及有效期管理，不是即时撤权通知。
3. 策略 baseline 的 `read_data` 无 permit；现有网关 `policy.build_request` 判的是能力 `invoke`，不能当成视图、列和行的 `read_data`。Data Hub 的 `ReviewedQuery`、本机版本账本与 `LocalDataQuery` 仅隔离注入，不是 HTTP／MCP 服务，也未接真实策略或目录。
4. 本机双检查和结构哈希可拒绝已观察到的变化；单 SQLite 整库快照回滚可重放旧状态，账本哈希与触发器不构成外部可信防回滚。现有直接用户测试 profile 明确拒绝 `act`，不能把它当作委托身份验证器。

## 2. 身份委托推荐契约（I）

- Runtime 保持原可信服务入口，用户令牌只存在于内存并传给网关；不从请求体、自报头、Run 发起人或服务身份推断当前用户。发起人和实际调用者若不一致，默认拒绝，其他委托场景需另行定义。测试使用签名的合成身份及纯 ASGI／HTTP 替身。
- 网关严格验证服务端调用身份和终端用户 access token 的签名、受控 issuer、明确非空 audience、时间、用途、主体种类和租户；缺失、冲突、服务身份、开发头或配置不全即拒绝。具体可用 claims、client、issuer/audience、时钟偏差与密钥轮换由正式 IdP 配置确认，不假定当前 token 已满足这些属性。
- 推荐网关换取专用于 Data Hub 受众的短期 OBO，并附原有网关签发的 act 断言；Data Hub **独立**验证两者签名、issuer、精确 audience、有效期／用途、OBO 用户主体和租户，以及 act 的主体、OBO hash、调用服务、Agent、Run／call 绑定。对缺失字段、身份不一致、过期或错误用途失败关闭；不接收自报 `X-AI-Dev-*`／`X-AI-Act` 作为权威。Data Hub 实现需新增专用委托验证适配，不能绕过现有直接用户 profile 的 `act` 拒绝。
- `jti` 存在不自动构成防重放：是否需要一次性消费须与只读调用幂等及多节点存储共同确定；本草案不依赖它保证撤权。不能把用户或 OBO 令牌、查询条件及行值写入日志或持久化，仅记最小关联标识和判定版本，日志保留细节待审批。

## 3. 双层判定与受控查询（P）

1. 网关保留现有能力级 `invoke` 判定，来源为验签身份和服务端能力目录；仅能力放行不授予读取数据。
2. Data Hub 每次对服务端登记的 `(tenant, view_id, view_version, manifest_generation, view/source digest)` 调用受控 `read_data` 判定，主体为验证后的真实用户，动作和资源类型不可由调用者指定；显式绑定 Agent、允许投影／过滤列、上限和策略版本。清单的租户必须等于已验证身份和 Agent 租户。判定服务不可用、超时、字段缺失或版本不匹配均拒绝。
3. 清单只由可信受控发布方与双审核流程提供，查询请求不得自带 SQL、底表映射、租户或授权。只允许已确认的单表直接视图、二进制精确租户过滤、列遮盖、参数化过滤和限行；真实数据源行租户标签真实性仍由数据所有者审核，并非 SQL 指纹能证明。
4. 正式策略需明确特定 DataView 的最小 permit、forbid 和可信发布流程；在批准、实现和隔离回归前继续保持 `read_data` 默认拒绝。不通过管理员通配或现有通用 `invoke` 放行替代。

## 4. 撤权及在途结果契约（R）

- 推荐结果从 Data Hub 对调用者释放前执行 T1/T2：校验用户和委托有效性、当前清单／策略可用、作用域及不可回退版本完全一致；策略／清单撤销、更新或重新授权的任一版本变化使已读取的旧结果丢弃，新请求需重新判定。清单与策略应从同一权威一致性快照读取；两次检查不是跨系统事务。
- 明确线性化边界：T2 之后、结果已被释放或在网络传输中的撤权不追溯召回；网关接到结果后无法证明 T2 之后没有撤权，不应宣称即时撤权或跨服务原子快照。若业务要求更强，应另行决定同步出站门闸／租约／锁和可用性代价，不能靠时间戳或 SSE 推断。
- 普通 JWT 本地验签／到期、OBO TTL 和版本复核不能证明 IdP 的账户／令牌即时撤销：要保证用户撤权需确定权威身份状态源、在线检查／推送失效和故障关闭契约；本轮不承诺实现。T2 不调用有副作用的自动重试。取消或请求失败不得返回已读取的部分数据。

## 5. 版本、防回滚与故障恢复（A）

推荐在正式环境采用**独立于查询副本的可信线性一致权威账本**，由经授权的受控发布者提交不可复用命令，按 `(tenant, view_id, kind)` CAS 原子追加单调版本、状态、前序摘要和清单／策略关联；可信签名证明发布来源但签名本身不能阻止恢复旧签名状态。查询端从权威源取得当前清单和策略的同一一致性快照，校验签名及绑定；权威不可达、版本／摘要冲突、未知密钥或无法证明新鲜性一律拒绝，不回退 SQLite 缓存。

此方案只有在权威源具备独立故障域、线性一致读写、不可回退保障及受控恢复时才能声称其覆盖的防回滚目标；具体技术（共识日志、受控防回退计数器或等价设施）和可信运维根尚未选定。不要假设分布式数据库、单调时钟、签名或普通备份天然具有该保证。发布与权威记录应采用同一权威事务作为提交点；如果实现需额外分离锚点和内容库，必须先证明崩溃两阶段恢复和不一致时拒绝，禁止为追平版本自动重放或自动放行。

备份恢复时先隔离读取／发布，核对独立权威高水位和签名；旧备份低于权威或丢失权威证明时不可恢复旧授权，需受控人工恢复和新版本重新审批。需明确多节点可用性、冲突处理、权威灾难恢复、密钥撤销及恢复方职责；任何措施在未证明前不得标记防回滚完成。

## 6. 隔离验证建议

不接真实网关、IdP或数据，使用临时 SQLite、进程内 ASGI／HTTP 替身、临时签名测试身份及合成租户。覆盖：服务与用户身份伪装、错受众／用途、OBO 和 act 签名／hash／主体／租户／Agent 绑定、委托重放边界、跨租户／越列与 read_data 默认拒绝、策略不可用、在途撤权／重新授权、旧响应丢弃、清单／策略不一致、权威源不可用及整库恢复反例。模拟的外部权威只能验证客户端协议与故障关闭，不能证明生产共识、密钥治理或真实防回滚。保留实际命令、结果和失败证据，不放宽断言。

## 7. 需人工确认的决定

- **I1**：是否采用“Runtime 用户令牌 → 网关 OBO + act → Data Hub 独立验证”作为隔离契约？请确认现有正式 IdP 是否能签发所需用户／租户 claims、受众和委托链；若不支持，先确定可信映射，不能由请求字段补齐。
- **P1**：是否采用能力 `invoke` 与 DataView `read_data` 两层独立授权，且生产 `read_data` 在明确资源级 permit 前保持默认拒绝？确认授权主体、角色来源、列与行策略及审批责任人。
- **R1**：是否接受 T2 后释放的边界，以及身份撤权需另有权威状态源？如要求更强的即时撤权，请确定目标、同步协议与可用性取舍。
- **A1**：是否以独立线性一致权威账本作为推荐方向？确认责任主体、不可回退实现和灾难恢复；暂未批准真实资源、密钥或服务。
- **J1**：是否要求对只读委托断言 `jti` 一次性消费？如要求，需确认跨节点去重保存期、重传语义与资源。若不要求，明确令牌短期有效期间可能重放的风险；不能把 hash 绑定当成重放防护。

批准上述具体契约前不增加网络入口、不接真实服务、不增加 `read_data` permit。后续若批准隔离实现，仍须对真实网络、凭据、生产配置和发布另行授权。
